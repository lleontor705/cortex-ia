# Design

## Planning join
REQ-RECON-001 maps to native boot evidence and the reconciliation service; REQ-RECON-002 maps to SQLite migration, proof, admission/Get/Result projections; REQ-RECON-003 maps to CLI/bridge/orchestrator permissions. All are implemented in ljr-1.1 and independently reviewed together.

## Service and proof
Add a service-owned Reconcile operation. CLI accepts only job ID and required bounded reason (1..1024 UTF-8 bytes after trimming). Bridge forwards host actor identity through an explicit bounded field if the service supports actor recording; local CLI audit distinguishes local operator from host session. Do not accept boot timestamps, proof JSON or a force flag from the caller.

Collect boot evidence through an internal platform provider: Windows native boot-time observation; non-Windows fails actionably until an equally trustworthy implementation exists. Require valid StartedAt and strict boot-after-start ordering with conservative uncertainty handling. PID absence or identity mismatch is never evidence of whole-tree termination. A real reboot ends all prior-boot processes, including descendants and transport workers. Use current observations, not the incident's reported timestamp as an input. Document wall-clock/boot-source precision assumptions; reject unavailable or ambiguous data.

Use schema version 13 with a STRICT append-only reconciliation proof table, foreign key to delegation_jobs, UNIQUE(job_id,attempt), bounded reason/actor/evidence, recorded start and PID, observed boot time/source and audit timestamp. Prevent update/delete of proof records using the repository's immutable-ledger convention. No change to prior receipt payloads or failure fields. Unknown future schemas fail closed. Existing version-12 databases migrate idempotently with no fabricated proofs.

Capture a candidate identity before evidence acquisition; under BEGIN IMMEDIATE re-read status=lost, attempt, StartedAt and execution identity and compare. Reject state/identity changes. Insert proof and append operational event in the same transaction. An existing matching proof returns idempotently even if current evidence collection is unavailable; it must not authorize a different attempt. No network or subprocess probing inside the authority transaction.

Admission excludes only lost jobs with a valid proof matching their current attempt/identity. Active accepted/starting/running/blocked jobs continue to fence regardless of stale proof. Pending or unconfirmed cancellation remains fenced until lost and proved. Get and Result derive reconciliation_required consistently from that same proof predicate. Preserve lost status, error code/message, timestamps and receipt output; do not manufacture a success receipt when none exists. Result may retain its no-receipt error while clearly exposing reconciled state through status. Do not restore, renew or recreate claims/leases/tokens. Other blocking jobs remain unaffected.

## Transport and permissions
Add CLI help and strict argument parsing for delegate reconcile. Add cortex_ia_delegation_reconcile with job_id and reason, classified as an orchestrator-only mutation; add an exact allow after Cortex family denies in orchestrator.md. Other roles remain denied by default. Do not close panes or emit a fabricated succeeded/cancelled event. Keep lost results distinguishable from success after reconciliation.

Admission errors include deterministic blocker ID and next action. Lost/unproven: inspect and explicitly reconcile if boot evidence qualifies; active: wait or request cancellation and await acknowledgement. Avoid claiming reconciliation is guaranteed for a current-boot lost worker. No automatic native fallback.

## Verification
New dedicated critical authority tests at most 250 lines use temporary SQLite and injected internal boot observations. Cover migration twice, prior-boot success, unchanged receipt/history, repeated call, concurrent uniqueness/rollback, active rejection, same-boot absent/reused PID rejection, missing evidence/start, pending cancellation and another blocker. Use disposable smokes for deeper migration/CLI integration. Existing cancellation harness covers actual bridge initialization, role rejection, argument forwarding, no pane close and truthful lost/reconciled result. No real AGY, production database or remote telemetry.

## Rollout and rollback
After independent PASS, the orchestrator may separately perform the user-authorized real recovery. First obtain a consistent SQLite API backup and a verified backup of the installed binary, then activate the newly built CLI at the path actually resolved by OpenCode (normally ~/go/bin/cortex-ia.exe) before any migration or reconciliation. Verify resolver/version. Running only a local binary and leaving the old installed CLI is insufficient. Schema 13 makes old binaries fail closed: never roll back just the binary after migration. Prefer a compatible forward fix and retain the new binary. Binary-only rollback is reversible before database migration. The database backup is for controlled recovery, never automatic restoration while work is live, which could revive old claims or discard later events. No live backup, installation or recovery occurs in this implementation task. Verify the exact real job proof, historical status and workspace admission read-only after the authorized operation; do not launch replacement work as a smoke.
